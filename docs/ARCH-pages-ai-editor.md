# AI, statement and storefront-editor pages

### `pages/ai/models.vue`

Company AI provider configuration. Lists providers and allows add, edit and delete through `/api/ai/providers`. The form supports OpenAI, OpenRouter, Gemini and custom OpenAI-compatible providers, including model ID, base URL where applicable, API key, vision capability and enabled state. A saved key is not returned to the form for display; replacement is optional when editing. Removing a provider can leave existing chats needing another available model. This page configures providers; it does not itself run a chat. AWS storefront editors offer two Sydney Amazon Bedrock choices through the shared controller/sandbox catalog: Claude Opus 5.5 as the default for coding and images, and Kimi K2.5 as the alternative. Opus invokes `au.anthropic.claude-opus-5-5`, with pinned Sydney/Melbourne destination models and its cross-region token quota (`L-A4430697`). The runtime uses a 1M-token context and caps generated output at 32,768 tokens. Older blocked Opus choices and Qwen are removed from this menu. Existing conversations keep their selected model until the user explicitly changes it; a design rerun sends the selected model explicitly. The AWS background dispatcher and both cloud image smoke checks also resolve the catalog default, rather than an older hardcoded Qwen choice. If preferred Opus is unavailable, the menu can still offer ready Kimi; an explicit Opus request must pass access validation and is never silently changed to Kimi.

An optional `BedrockBearerSecretArn` deployment parameter injects `AWS_BEARER_TOKEN_BEDROCK` into the controller and sandbox through ECS Secrets; the Pi SDK prefers this bearer token for model requests. Repository/storage operations retain company-scoped AWS roles. No API-key value is stored in source, deployment state or the model form. The execution role is granted access to the configured Bedrock secret ARN in addition to its existing runtime secrets. Without that parameter, model calls use the sandbox ECS task role.

The controller checks foundation-model authorization/entitlement/region, the active inference profile and exact destination ARNs, and nonzero inference quotas before compute. With bearer authentication it additionally requires a completed Converse stream using the configured key before offering a model or starting a task; failed billing/key probes remain unavailable. IAM authentication requires Marketplace agreement availability. A small nonstreaming reply or an active profile alone is insufficient. Before AWS sandbox reuse/start, the controller refreshes the company-owned IAM policy with the exact account inference-profile ARN and destination foundation-model ARNs; no wildcard inference resources are granted. Enabled company-owned BYOK models remain available alongside Bedrock. Legacy GCP editors retain their built-in choices.

### `pages/ai/usage.vue`

AI consumption dashboard from `/api/ai/usage`. Choose 7, 30, 90 days or all time; inspect total/input/output tokens, billed cost, daily usage and recent runs. The page includes a warning when token rates are not configured, so cost figures should not be treated as authoritative in that state.

Provider and usage readiness checks only select from the existing tables with `LIMIT 0`. Their definitions belong to `schema.zmodel`; page requests do not create tables or indexes. A missing table returns 503, and failed readiness checks can retry after setup is restored.

The AI Usage endpoint also depends on storefront agent sessions for chat titles. Agent-session, source, design-profile and page readiness helpers use the shared SELECT-only table check in `schemaReadiness.ts`, rather than runtime CREATE/ALTER/index/constraint changes. This covers the transitive dependency that previously made the usage GET fail on a read-only connection. Cloud source/deployment workflows remain separate from readiness checks.

### `pages/statement/[id].vue`

Statement review resolves `StatementBatch` ownership through `/api/organization/context` before loading bank choices or actions. Its Company / branch field is locked to the saved statement's owner. All statement bank/classification/execution routes resolve authorized request scope; head-office users can work on a branch statement while their login remains in head office. Moving a statement to another company is not offered.

Bank-statement review and execution page for a particular statement ID. Staff inspect extracted rows, assign or auto-find matching operations, review classification, and execute an individual row or the batch through the `/api/statement/find-operation`, `/api/statement/execute-row` and `/api/statement/execute` flows. Extraction and assignment do not by themselves post money movements; execution is the state-changing step. The statement-processing architecture and matching rules are in `ARCH-ai-chat.md`.

### `pages/storefront/editor.vue`

Seller-facing full-stack storefront editor. Select a storefront page slug, load its saved configuration with `GET /api/ecommerce-cms/storefront-pages/{slug}`, and edit it alongside an iframe preview and AI chat slideover. The page can seed bundled defaults for known slugs. Before editing it checks/creates storefront source via `/api/ecommerce-cms/storefront-source`, and checks the design-onboarding state via `/api/ecommerce-cms/storefront-design`. Saving dirty page config uses `PUT /api/ecommerce-cms/storefront-pages/{slug}`; publishing uses `POST /api/ecommerce-cms/storefront-source/publish`. A preview update triggers deployment-status polling, then reloads the iframe when the new deployment is ready; failure and timeout are surfaced separately. The source/deployment flow is distinct from the old `pages/store/[[company]]` routes described as historical in `ARCH-pages-store.md`.

AWS preview editing: Pi works on the assigned repository's `preview` branch. After an ordinary completed turn, the sandbox save operation verifies the checked-out branch is `preview`, runs `npm run build`, checkpoints the changes, and pushes only `HEAD:refs/heads/preview`. A build failure or another checked-out branch prevents that save. The AWS controller requests deployment status after a changed save, serializing Amplify build creation per company and ensuring a job targets the current branch commit. An older successful job cannot satisfy the new preview refresh. Publishing remains a separate authenticated operation; an editor message does not directly push `main`.

Design onboarding and chat share `server/utils/storefrontModel.ts` for model-key format validation. Both accept legacy model keys, `bedrock:` keys (including Kimi K2.5 and Opus 4.5's numeric `:0` model-version suffix), and `byok:` provider UUIDs. Bedrock suffixes are limited to one numeric version segment; malformed suffixes are rejected before saving or starting. This format check does not authorize a model: `startStorefrontInteraction()` still checks AWS model availability and resolves company-owned BYOK providers before reserving an interaction.

Both entry points pass the authenticated `session.data.id` as `userId` and `session.data.companyId` as `companyId` to `startStorefrontInteraction()`. The orchestrator requires both identities along with the conversation ID and prompt; browser-supplied identity fields are ignored.

`startStorefrontInteraction()` validates required identities/prompt before reserving a conversation. Local queue reservations clear the previous interaction ID and return their exact `updated_at` version. Explicit controller rejections (4xx except timeout/rate-limit responses) release only that same unaccepted reservation. Retries and status polling recover reservations older than two minutes only while the interaction ID and pending prompt remain empty, dispatch is not queued/dispatching/running/stopping, and no matching environment is processing. Accepted tasks and ambiguous network failures are not cleared merely because a response was lost. This prevents pre-dispatch failures or Storetools restarts from leaving design onboarding queued indefinitely; the existing controller lifecycle handles accepted tasks.

The starter includes an empty `company-info.json`. After clone, `.markit/setup.sh` installs locked dependencies and runs `scripts/sync-company-info.mjs` before opening the AI session. It fetches the DB-backed public company `/store` endpoint, keeps only public identity/logo/contact/address/social/currency fields and rejects mismatched company IDs. The onboarding prompt and repository agent notes require this file as the factual brand source rather than treating the business-description field as a company name. A `prebuild` hook refreshes it; transient API failures can reuse a valid same-company snapshot. The Vue catalog initializes from this snapshot and replaces it with live API data; products, prices and checkout remain live. The AWS template packer rejects a tenant-filled starter snapshot.

Initial design uses `edit-sandbox/design-workflow.js` as an enforced two-stage workflow inside the isolated company repository cloned from the starter. The first stage saves the canonical design skill plus `design/design-system.json`, `design/tokens.css` and `design/rollout.md`; `design/brief.md` and the source inventory preserve the input/context. The second stage reads those artifacts, imports the generated tokens into real `src/` code, applies the design and runs a bounded test/fix loop. Empty replies, documentation-only changes, failed builds and failed mobile/desktop browser checks cannot complete the task. `design/verification.json` records the changed source files, browser results and a content digest; save rejects missing or stale verification. Browser screenshots remain outside Git under `.markit/design-checks/`.

The controller persists `designValidation` in the existing runtime-result JSON. The design profile requires that evidence and a new saved commit, then waits for the latest AWS preview deployment to be ready. An old completed no-op run is returned as failed with a retry explanation. The editor refreshes its preview URL/deployment ID before opening the finished design. `orchestrator/aws-runtime.js` also supplies `VITE_COMPANY_ID`, API URL and editor origin to each company sandbox so browser checks use that company's storefront configuration.
